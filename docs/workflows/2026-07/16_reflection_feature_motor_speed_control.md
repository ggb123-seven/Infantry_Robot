# 单个 M3508 电机速度环与缓启动开发反思

**日期**: 2026-07-16
**提交类型**: feature
**修改文件数**: 19 个文件

## 1. 概述

为单个 M3508/C620 增加输出轴速度 PID、目标限幅、缓启动和电流指令限幅，并提供可由 Ozone 监视和修改的 PID 参数。该模块不代表整个底盘速度闭环，不包含底盘运动学、车体速度闭环或多电机同步控制。最终按照参考工程的 task/module/component 分层整理代码：`motor_chassis` 负责主任务和设备 I/O，`motor_speed_control` 只负责这一台电机的速度控制算法与状态。

## 2. 修改内容

### 修改的文件

- `User/task/motor_chassis.c/.h`：保留现有单个 M3508 电机任务入口、周期调度、RM 电机反馈更新和控制指令下发。
- `User/task/motor_speed_control.c/.h`：实现速度 PID、目标限幅、斜坡缓启动、异常复位、调试反馈和 Ozone 在线调参。
- `CMakeLists.txt`、`MDK-ARM/Infantry_Robot.uvprojx`：将新增速度控制源文件加入两套工程。
- `agent.md`：补充单行排版及 while 循环调用注释约定。
- `.auto-embedded` 规格和任务记录：沉淀控制单位、模块职责和验证结果。

### 主要变更

- 速度目标、限幅目标、缓启动目标和真实速度统一使用减速箱输出轴 rpm。
- 速度 PID 输出为转子侧电流指令 A，只调用现有 `PID_Init`、`PID_Calc` 和 `PID_Reset`，未新增软件电流环。
- 目标速度限制为 `+-300 rpm`，缓启动斜率为 `150 rpm/s`，电流指令限制为 `+-4 A`。
- `g_motor_speed_pid_tune` 位于 RAM，可在 Ozone 中监视并调整 `Kp/Ki/Kd`。
- 反馈结构体相邻保存目标速度和真实速度，并集中注明单位、含义和故障状态。

## 3. 遇到的问题

1. 早期把“速度 PID 输出电流指令”误解成另有软件电流环，控制边界表述不准确。
2. 首版没有把目标速度和真实速度集中放入同一个反馈结构体，不利于调试器对比。
3. 首版 PID 参数只作为编译期配置，未提供稳定的 RAM 全局调参入口。
4. `motor_chassis` 与 `motor_speed_control` 的职责多次放反，出现任务入口位于算法模块或任务文件包含过多包装函数的方案。
5. while 循环曾展开大量状态计算和空值处理，主流程不够直观。
6. 部分简单声明和函数调用被机械拆行，偏离项目期望的紧凑排版。

## 4. 根本原因分析

### 为什么会出现这些问题?

- 没有在实现前先确认 C620 接口语义：`MOTOR_RM_SetTorqueCurrent` 负责电流指令换算与缓存，不代表应用层实现了电流闭环。
- 只关注算法功能，未先把调试观察、在线调参和任务编排作为同等重要的接口需求。
- 未在第一版之前阅读用户指定参考工程，凭通用分层经验推断了文件职责。

### 编写时遗漏了什么?

- 没有先画清数据流：宏目标 rpm -> 限幅目标 rpm -> 缓启动目标 rpm -> PID -> 电流指令 A。
- 没有先列出每个文件的唯一职责和允许依赖。
- 没有把“while 主要直接调用函数”和“短代码保持单行”作为提交前检查项。

## 5. 调整过程

1. 核对 `motor_rm.c` 和 C620 协议，确认反馈速度与电流指令的单位和边界。
2. 使用项目已有 PID 库建立速度环，并增加目标限幅、缓启动和输出限幅。
3. 增加 RAM 中的 `volatile` PID 调参结构体，同时保留非零 D 项能力和反馈微分状态预置。
4. 将目标速度与真实速度纳入同一个反馈结构体，并补齐关键中文注释。
5. 对照 `F:\RM\未命名文件夹` 的框架，确定 task 负责设备 I/O 和流程，module 负责算法状态与 API。
6. 删除多余的一对一包装函数，使 `motor_chassis` 的 while 循环直接呈现反馈、控制、输出和等待流程。
7. 同步 CMake、Keil、规格、任务记录并完成构建和机械门禁验证。

## 6. 经验总结

### 核心结论

- 电机控制代码必须明确区分闭环类型、反馈量、控制输出和设备接口，不能因输出量是电流就称为电流环。
- 调试反馈结构体应围绕实际观察需求组织，相互对比的目标量与真实量应放在一起并统一单位。
- task/module/component 的边界应由工程现有框架决定，文件命名不能替代职责核对。

### 预防策略

- 实现控制功能前先记录完整数据流、单位、限幅位置和离线行为。
- 新模块开工前先阅读同仓库或用户指定参考工程的任务入口、主结构体和 API 形态。
- 提交前逐项检查 while 主流程、全局调试变量、结构体字段和注释是否满足调试需求。

## 7. 知识提炼

### 可复用模式

- task 只编排设备 I/O、模块 API 和周期调度。
- module 用一个主结构体集中保存 parameter、setpoint、feedback、PID 和 output。
- 调试器可修改参数通过独立 `volatile` RAM 结构体输入，每周期复制、校验后再应用到算法对象。

### 应避免的反模式

- 在算法模块中拥有 RTOS 任务入口或直接依赖设备驱动。
- 为每个设备库函数增加一对一公共包装，导致调用链变长但没有增加策略。
- 在 while 中展开所有控制细节，使主循环难以扫描。

### 类似任务检查清单

- [ ] 确认反馈量、设定量和输出量的单位。
- [ ] 区分软件闭环与设备指令接口。
- [ ] 确认目标、反馈、限幅和缓启动状态可被调试器观察。
- [ ] 确认 PID 参数可在线修改且非法值有失效处理。
- [ ] 对照现有工程确定 task/module/component 职责。
- [ ] 检查离线、重新上线和非有限值路径均输出零指令。
